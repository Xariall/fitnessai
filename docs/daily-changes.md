**Позже в тот же день: подключил онбординг и фолбэки к системе удаления сообщений.**

Пользователь заметил, что в Telegram-чате удаляются не все сообщения бота — расследовал
механизм навигации (`bot/helpers.py`: `send_and_track`/`delete_tracked`, паттерн «одна
отслеживаемая карточка» через `last_bot_msg_id` в FSM state) и нашёл два реальных пробела:

- `bot/handlers/start.py` — весь 7-шаговый онбординг вообще не участвовал в этой системе,
  использовал сырые `message.answer()`/`callback.message.answer()`. Переведён целиком на
  `send_and_track`: каждый следующий вопрос удаляет предыдущий, ответы пользователя
  удаляются (`delete_user_msg=True`), подтверждения выбора («Цель: 🔥 Похудение ✅»)
  склеены с следующим вопросом в одно сообщение вместо отдельного, которое раньше никогда
  не удалялось. Финальное сообщение онбординга тоже теперь трекается — передаёт эстафету
  главному меню.
- `bot/handlers/direct.py` — все `except`-фолбэки ("Не удалось загрузить данные...") и
  валидационные подсказки использовали сырой `message.answer()`, из-за чего никогда не
  подчищались. Переведены на `send_and_track`.
- Отдельно перепроверил гипотезу про несогласованность `delete_user_msg` в `direct.py`
  (несколько похожих обработчиков передавали флаг по-разному) — оказалось НЕ багом:
  функции, вызываемые из `/today`/`/stats`/`/progress` (slash-команды), намеренно не
  удаляют сообщение пользователя (как в любом обычном Telegram-боте команда остаётся
  видна), а вызовы из инлайн-кнопок вообще не имеют независимого пользовательского
  сообщения для удаления. Не менял эту часть.
- Файлы не закоммичены на момент записи (`bot/handlers/start.py`, `bot/handlers/direct.py`
  изменены после коммита `46ac444`).

## 2026-08-18

**Настройки питания перед первым планом + требование рынка СНГ/Казахстан.**

- Задача: при первой генерации плана питания (или по явной просьбе «обнови настройки
  питания») агент должен спросить пользователя про 1) какие продукты обычно есть дома,
  2) любимые/нелюбимые блюда, 3) бюджет на питание — и использовать это при сборке плана.
  Плюс: все продукты/блюда в планах — с рынка СНГ, реалистичные для Казахстана, без
  западной экзотики (киноа, авокадо-тост и т.п.) без явной просьбы.
- Новая колонка `users.nutrition_preferences jsonb` (nullable, без default — `NULL`/`{}`
  значит «настройки ещё не заполнены»). Хранит `{usual_products, liked_foods,
  disliked_foods, food_budget}`. Добавлена в `migrations/001_schema.sql` (описание
  конечного состояния) и накачена на живую Railway Postgres тем же способом, что и
  первичная схема — `railway ssh -s bot`, но через `echo <base64> | base64 -d | python3`
  вместо `python3 -c "..."`: `railway ssh` наивно склеивает argv через пробел и
  передаёт на удалённый шелл без сохранения кавычек, поэтому любые `(`/`'`/`"` внутри
  `-c`-аргумента ломают удалённый парсинг (`sh: Syntax error: "(" unexpected`), а
  обёртка в `sh -c "... | ..."` тоже не работает — второй проход join склеивает
  `-c echo <base64>` в позиционные параметры вложенного `sh -c`, и сама полезная нагрузка
  в python не попадает (пустой pipeline, exit 0, но без эффекта). Рабочий способ: одним
  argv-элементом передать голый pipeline `echo <base64> | base64 -d | python3` без
  вложенного `sh -c` — тогда удалённый шелл, через который `railway ssh` и так
  прогоняет команду, сам корректно разбирает pipe.
- `db/models.py` — `User.nutrition_preferences: Optional[dict] = None`.
- `agent/tools/nutrition.py` — два новых tool'а: `get_nutrition_preferences` (читает
  колонку, `{}` если пусто) и `save_nutrition_preferences` (перезаписывает все 4 поля
  разом, без partial-update — осознанно просто, апдейт настроек всегда идёт через тот
  же 3-вопросный диалог). `generate_nutrition_plan` подмешивает сохранённые настройки
  в промпт LLM (блок «Настройки питания пользователя») + жёсткое правило рынка СНГ/КЗ
  и явный запрет на экзотику без запроса пользователя.
- Промпт (оба пути — `agent/prompts/system.py` — живой дефолтный плоский граф, и
  `agent/prompts/nutrition.py` — router за флагом `ENABLE_SUBAGENT_ROUTER`, держал их

**Позже в тот же день: убрал спам от утреннего/вечернего чек-ина (bot/scheduler.py).**

- Проблема: `_send_morning_checkin`/`_send_evening_summary` слали `bot.send_message`
  напрямую, без какого-либо трекинга — каждый день добавляли новое сообщение в чат,
  старые никогда не удалялись (в отличие от остальной навигации бота, которая давно
  переведена на паттерн «одна отслеживаемая карточка», см. запись про онбординг выше
  и `bot/helpers.py`: `send_and_track`/`delete_tracked`).
- Не стал переиспользовать `send_and_track`/навигационный `last_bot_msg_id` напрямую —
  он завязан на `Message`/`CallbackQuery` (входящий апдейт) и на FSMContext, который
  создаётся aiogram-миддлварой из живого события. У проактивной рассылки из
  `run_scheduler` этого нет — только `bot` и список `telegram_user_id` из БД. К тому же
  переиспользование ОБЩЕГО `last_bot_msg_id` было бы неверным: удаляло бы что угодно,
  что сейчас открыто у пользователя (например, открытую карточку тренировки), а не
  вчерашнее чек-ин-сообщение — это не то поведение, которое просили.
- Решение: у утреннего и вечернего чек-ина — свои независимые ключи в FSM-хранилище
  (`morning_checkin_msg_id`, `evening_summary_msg_id`, отдельно от навигационного
  `last_bot_msg_id`). `_state_for_user()` вручную строит `FSMContext` через
  `StorageKey(bot_id, chat_id=user_id, user_id)` — то же `MemoryStorage`, что и у
  `Dispatcher` в `bot/main.py` (теперь прокидывается в `run_scheduler(bot, dp.storage)`
  явным параметром). Для приватных чатов `chat_id == user_id`, что и так уже
  предполагается остальным ботом.
- `_send_tracked()` — общий хелпер: удалить предыдущее сообщение ЭТОГО типа чек-ина
  (если было) → отправить новое → запомнить `message_id`. Ошибка удаления (сообщение
  уже стёрто вручную) не блокирует отправку — та же логика, что в `delete_tracked`.
- Известное ограничение: `MemoryStorage` не персистентный — при рестарте бота
  (передеплой) трекинг обнуляется, один раз после рестарта старое сообщение не
  удалится (тихо, без ошибки), дальше трекинг продолжается штатно. Тот же trade-off
  уже существует у общего `last_bot_msg_id`, ничего нового не вносили.
- `tests/test_scheduler.py` — 5 тестов на `_send_tracked`/`_state_for_user`: первая
  отправка не удаляет, вторая удаляет предыдущую, ошибка удаления не блокирует
  отправку, утренний и вечерний ключи независимы, `chat_id == user_id` в собранном
  `StorageKey`.
- Задеплоено на Railway через `railway up -s bot --ci --detach` (сервис не подключён
  к GitHub — `git push` для него ничего не делает, см. запись про деплой выше).
